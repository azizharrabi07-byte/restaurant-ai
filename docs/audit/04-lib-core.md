# Lib Core Audit

Scope: `src/lib/{owner-auth,worker-auth,worker-permissions,worker-invite,rate-limit,order-utils,menu-mapping,menu-sync-guard,qr,utils,format,constants,use-orders,image-utils}.ts` and the `*.test.ts` siblings that exist for five of them (`worker-auth`, `worker-permissions`, `rate-limit`, `order-utils`, `menu-sync-guard`).

## Verdict

This slice is the strongest part of the codebase: input validation is strict, pricing is server-computed, the cross-restaurant IDOR is genuinely closed, and the dev auth bypass is correctly gated. It is **not** shippable as-is, because three business rules the code itself documents are not enforced: workers can reopen accepted/paid orders (`canSetArbitraryStatus` exists but is never called), worker sessions never expire server-side and logout does not revoke them, and the owner logout does not revoke the Supabase refresh token. Separately, the menu sync guard validates a payload and then returns the **raw, unvalidated object** (`menu-sync-guard.ts:180`), so `position`/`isAvailable`/`isPublished` walk straight into DB writes, and the QR URL embeds a slug that is recomputed from the restaurant name on every sync, so renaming a restaurant 404s every already-printed QR code. Money is rounded to 2 decimals here while the rest of the pipeline (import, scan, display) uses the 3-decimal TND millime.

## Required behaviour

Derived from the module doc comments plus the call sites:

| Module | Contract (as documented and consumed) |
| --- | --- |
| `owner-auth.ts` | Service-key-only sign-in; access/refresh pair held in an `HttpOnly` cookie; every protected route verifies the access token via `auth.getUser`; lazy rotation via the gotrue refresh grant; the `SUFRA_AUTH_DISABLED` dev bypass is impossible on a production build. |
| `worker-auth.ts` | Session token minted by the server (128-bit hex) and stored on the `workers` row; all API routes resolve identity from Bearer/cookie, never from the body. |
| `worker-permissions.ts` | Server-enforced role matrix: cashier accepts only, manager/owner may mark paid, owner alone may rewrite arbitrary states. |
| `worker-invite.ts` | 24 h invite TTL; server-minted 128-bit invite tokens and 256-bit session secrets. |
| `rate-limit.ts` | In-memory sliding window keyed by client IP, correct boundary arithmetic, bounded memory. |
| `order-utils.ts` | Strict line schemas (unknown keys rejected), server-computed `price × qty` totals, client-supplied `total` never trusted. |
| `menu-mapping.ts` / `menu-sync-guard.ts` | The sync endpoint must persist only a validated payload, never ids owned by another restaurant, never an orphan category, never a cross-restaurant category reference. |
| `qr.ts` | Deterministic QR data-URL for a given value; bulk download. |
| `utils.ts` | `appBaseUrl()` yields the origin the user actually reached (or the configured app URL) for links and QR codes. |
| `format.ts` | TND amounts render at millime precision. |
| `constants.ts` | Shared domain types/data importable from both server and client. |
| `use-orders.ts` | Poll cloud orders every 3 s without clobbering fresher local mutations; optimistic mutations reconcile with the server. |
| `image-utils.ts` | Prepare a scanned image for upload, keeping OCR legibility while respecting the file-size cap. |

## Findings

### LIB-01 · High · `worker-permissions.ts` + `PATCH /api/orders/[id]` · VERIFIED
- **Evidence:** `worker-permissions.ts:25-28` documents "Owners alone may reopen or rewrite arbitrary states", but `grep` shows `canSetArbitraryStatus` is referenced **only** by its own test (`worker-permissions.test.ts:40-42`). The route builds the update from `VALID_STATUSES = new Set(["pending","accepted"])` (`[id]/route.ts:10`) and applies it with no role check (`[id]/route.ts:82-90`); the only role gate is `canMarkPaid` (`[id]/route.ts:77`).
- **Impact:** any cashier or manager can PUT `status:"pending"` and pull an accepted — or already paid — order back to the pending column, re-notifying the kitchen. Because `is_paid` is untouched, an order can end up `status="pending", is_paid=true`, a state no dashboard renders correctly. The prior audits call both helpers "dead code, harmless" (`FINAL-AGENT2-AUDIT.md:100`, `SECURITY-REPORT-ROUND-2.md:92`); that is wrong for `canSetArbitraryStatus` — removing it would delete a documented gate that nothing else provides. `canAcceptOrder` is the genuinely redundant one (the status mapping already lets every role send `accepted`).
- **Fix:** enforce it in the PATCH route before the mapping, e.g. `if (body.status === "pending" && !canSetArbitraryStatus(role)) return 403`, and add a regression test asserting a Cashier `PATCH {status:"pending"}` → 403 while an Owner gets 200. Delete `canAcceptOrder` or replace the `VALID_STATUSES` branch with it so the tested predicate is the executed one.

### LIB-02 · High · `worker-auth.ts` + `logout` · VERIFIED
- **Evidence:** `WORKER_SESSION_MAX_AGE = 604_800` (`worker-auth.ts:20`) is used only as a cookie `maxAge` (`api/auth/worker/accept/route.ts:135`); `lookupWorkerByToken` filters solely on `session_token` with no expiry predicate and no expiry column in the select (`worker-auth.ts:65-69`). Migration 1002 adds only `session_token text UNIQUE` + an index (`1002_production_readiness.sql:148-152`). `POST /api/auth/logout` clears cookies and nothing else (`api/auth/logout/route.ts:5-9`).
- **Impact:** the 7-day window is client-side only. A token captured from a shared tablet, a browser profile backup, or a log stays valid **forever**; logging out does not stop it, and there is no way for an owner to revoke a lost device. This is the single largest auth lifetime hole in the app.
- **Fix:** add `session_expires_at timestamptz` to `workers` (migration), set it in the accept route, check `session_expires_at > now()` in `lookupWorkerByToken`, and null `session_token` + `session_expires_at` for the logged-out worker in the logout route (requires the token there, which the route already has in the cookie).

### LIB-03 · High · `owner-auth.ts` + `logout` · VERIFIED
- **Evidence:** `SESSION_MAX_AGE = 60*60*24*60` (`owner-auth.ts:18`); `refreshOwnerTokens` will exchange a stored refresh token for a fresh pair indefinitely (`owner-auth.ts:128-152`); `clearOwnerSessionCookie` only writes an empty cookie (`owner-auth.ts:236-245`) and the logout route does nothing else (`api/auth/logout/route.ts:5-9`).
- **Impact:** a leaked refresh token survives logout for up to 60 days and keeps minting valid access tokens. "Log out" on a public terminal does not end the session.
- **Fix:** in the logout route, revoke server-side first — `POST ${NEXT_PUBLIC_SUPABASE_URL}/auth/v1/logout` with the access token (service key as `apikey`/`Authorization`, mirroring `refreshOwnerTokens`) before clearing the cookie; ignore a non-2xx and clear the cookie regardless.

### LIB-04 · High · `order-utils.ts` · VERIFIED
- **Evidence:** `lineTotal` and `computeOrderTotal` round to 2 decimals (`order-utils.ts:162`, `order-utils.ts:176`), while the currency is millime-precision everywhere else: `formatDT` renders 3 decimals (`format.ts:1-8`), OCR import rounds to 3 (`menu-import.ts:95`), and the scan parser rounds to 3 (`menu-scan.ts:377`).
- **Impact:** a product priced from an imported menu at 3 decimals (e.g. 4.755 DT — reachable via `sanitizePrice`, which keeps the third decimal) is charged as 4.76, and `orders.total` / `order_items.price_snapshot` disagree with the cart the guest saw. Per-line rounding also accumulates up to 0.005 DT per line (60 lines → 0.30 DT).
- **Fix:** make the money precision uniform at 3 decimals: `Math.round(price*qty*1000)/1000` in `lineTotal` and `Math.round(total*1000)/1000` in `computeOrderTotal` (or store integer millimes and format at the edge). Add a test that `lineTotal(4.755, 1) === 4.755` and that a mixed 3-decimal basket survives `computeOrderTotal` unchanged.

### LIB-05 · High · `menu-sync-guard.ts` + `PUT /api/menu` · VERIFIED
- **Evidence:** `validateSyncPayload` accepts, but never rebuilds, the payload — it returns `{ ok: true, payload: payload as MenuSyncPayload }` (`menu-sync-guard.ts:180`), a cast of the raw object. The route then writes fields the guard never inspected: `sort_order: c.position` (`api/menu/route.ts:270`, unchecked — the guard validates only `id` and `name`, `menu-sync-guard.ts:118-127`), `is_available: p.isAvailable ?? true` (`api/menu/route.ts:324`, type never checked — the guard checks only id/category/name/price/imageUrl/description, `menu-sync-guard.ts:129-150`), and `is_published: r.isPublished` (`api/menu/route.ts:186`, `:204`, never checked — `menu-sync-guard.ts:161-177`).
- **Impact (three concrete writes a buggy client can force):**
  1. **Missing/invalid `sort_order`** — a category sent without `position` produces `sort_order: undefined`, which JSON serialization drops, so the upsert omits the column; `NaN` becomes `null`. Categories then order unreliably for every guest (`menu/[slug]/[token]/page.tsx:34`).
  2. **Non-boolean `isAvailable`** — `"no"`/`1` is written to a boolean column and the whole sync fails with `UPSERT_PRODUCTS` 500 (`api/menu/route.ts:332-334`), i.e. one bad field permanently blocks menu publishing for that restaurant, with no way to fix it from the UI.
  3. **Non-boolean `isPublished`** — a truthy string unpublishes/publishes unpredictably.
- **Fix:** make the guard reconstruct the object it returns — coerce/normalize at the boundary (`position: Number.isInteger(c.position) ? c.position : 0`, `isAvailable: p.isAvailable !== false`, `isPublished: r.isPublished === true`) and reject when the *type* is wrong rather than accepting anything non-null (the same style already used for `price`). A sanitizing return value also removes the `as` cast, which is what makes this class of hole possible.

### LIB-06 · High · `menu-mapping.ts` + `qr.ts` call sites · VERIFIED
- **Evidence:** the sync payload derives the slug from the current name — `slug: slugify(state.restaurantName || "my-cafe")` (`menu-mapping.ts:100`) — and the route writes it on every sync, both on update (`api/menu/route.ts:179`) and insert (`api/menu/route.ts:197`). The QR URL is built from that same slug plus the table token: `` `${base}/menu/${slug}/${token}` `` (`(owner)/dashboard/tables/page.tsx:25`), and the guest page resolves the restaurant **by slug** (`.eq("slug", slug).single()`, `menu/[slug]/[token]/page.tsx:22-25`, `notFound()` on miss).
- **Impact:** printed QR standees are the product's core artefact and they are not durable. Renaming the restaurant (a first-class onboarding field) changes the slug, and every already-printed QR code resolves to `notFound()` — silently, with no redirect and no slug history.
- **Fix:** freeze the slug when the restaurant row is created (only generate on insert; ignore it on update), or add a `restaurant_slugs` alias so old slugs keep resolving, or key the QR on the immutable restaurant id instead of the slug. Also record the alias lookup in the guest page before `notFound()`.

### LIB-07 · High · `use-orders.ts` · VERIFIED
The hook is a bare `setInterval(load, 3000)` (`use-orders.ts:50`) with no in-flight guard, no ordering, no visibility handling and no error path. Observable consequences, all from `use-orders.ts:31-71`:
- **Stale overwrite** — responses carry no sequence id and are never aborted, so a slow earlier poll lands after a newer one and replaces fresher state with older data (`:39-44`).
- **In-flight overlap** — `setInterval` fires whether or not the previous `fetch` resolved; with the 3.6–11 s menu fetches the prior report measured (`PERFORMANCE-OCR-REPORT.md:399`), requests pile up and each one independently overwrites the list.
- **Silent failure** — `if (!res.ok) return` (`:37`) discards 401s, 429s and 500s, and `if (data.cloud)` (`:39`) skips `cloud:false` bodies, so after a session expiry the dashboard renders the last successfully fetched list **forever**, with no error and no "reconnecting" state. A cashier sees an order list that stopped updating.
- **No visibility handling** — no `visibilitychange` listener, so background tabs are throttled to ≥60 s and burst on focus.
- **Rejected mutations are invisible** — `patch` ignores the response entirely (`:57-71`); a 403 ("your role cannot mark orders paid") or a 429 leaves the optimistic `paid` badge on screen with no message.
- **PATCH is sent unconditionally** — the optimistic update requires `o.status === "pending"` (`:77`) but the request does not (`:87-91`), so clicking a card already accepted by another worker leaves the UI showing the original accepter while the server rewrites `accepted_by` to the clicker (last-writer-wins, `[id]/route.ts:97-100`). UI and DB disagree until the next poll.
- **Minimal correct fix** — one effect, one in-flight slot, one abort per tick, ordered application, and a surfaced error:
```ts
useEffect(() => {
  if (!live) return;
  let stopped = false, inFlight = false, seq = 0, applied = 0;
  let ac: AbortController | null = null;
  const load = async () => {
    if (inFlight || (typeof document !== "undefined" && document.hidden)) return;
    inFlight = true;
    ac = new AbortController();
    const mine = ++seq;
    try {
      const res = await fetch("/api/orders", { signal: ac.signal, cache: "no-store" });
      if (!res.ok) { if (!stopped) setError(res.status); return; }
      const data = (await res.json()) as OrdersResponse;
      if (stopped || !data.cloud || mine < applied) return;
      applied = mine;
      setError(null);
      setOrders(data.orders.map((o) => (o.isPaid ? { ...o, status: "paid" as const } : o)));
    } catch { /* keep last known state */ }
    finally { inFlight = false; }
  };
  void load();
  const t = setInterval(load, 3000);
  const onVis = () => { if (!document.hidden) void load(); };
  document.addEventListener("visibilitychange", onVis);
  return () => {
    stopped = true; ac?.abort(); clearInterval(t);
    document.removeEventListener("visibilitychange", onVis);
  };
}, [live]);
```
Also make `patch` return the `Response` and revert the optimistic state + surface a toast when it is not ok, and gate the accept PATCH on `status === "pending"` the way the optimistic update already is.

### LIB-08 · Medium · `rate-limit.ts` · VERIFIED
- **Evidence:** `clientIp` returns the **first** `X-Forwarded-For` entry verbatim (`rate-limit.ts:25-30`) — a header the caller controls — and the bucket key is built from it (`rate-limit.ts:50`). `buckets` is a module-level `Map` (`:14`) that is pruned only when `size > 4096` **and** only after a *successful* push (`:71`); `pruneBuckets` deletes a key only when its **last** timestamp is already older than the current namespace's cutoff (`:75-82`).
- **Impact:** an unauthenticated client can send a unique `X-Forwarded-For` per request, so every request creates a key that survives pruning for the whole window — unbounded memory growth (a self-inflicted OOM) and, once past 4096 keys, an O(n) map scan on every accepted request, i.e. the limiter becomes the amplifier. The header comment (`:9-11`) acknowledges that XFF is trusted but not that trusting it makes the map attacker-sized. Secondary: when the header is absent or blank the fallback is the constant `"127.0.0.1"` (`:33`), so behind a proxy that strips XFF (or with an empty leading entry, `:28-29` then `:32`) **all users share one bucket** and one noisy client 429s everyone.
- **Fix:** key on an address the client cannot spoof (the right-most hop your own proxy appends, or a platform header such as `cf-connecting-ip`/`x-vercel-forwarded-for`), and make the map self-bounding — on insert, if `size > MAX_KEYS`, evict the least-recently-active key regardless of the cutoff. Keep the "smallest" fallback but treat it as a single shared bucket deliberately.
- **Algorithm correctness (verified, not a defect):** pruning uses `head > cutoff` (`:57-61`), i.e. only timestamps strictly inside the window are kept — correct sliding-window semantics with no off-by-one; `retryAfterSeconds = max(1, ceil((oldest - cutoff)/1000))` (`:63-67`) is the correct time until the oldest entry leaves the window. It is `Date.now()`-based (`:48`), so a backwards clock jump extends the window for existing entries — acceptable for this use, worth a comment.

### LIB-09 · Medium · `menu-sync-guard.ts` + `PUT /api/menu` · VERIFIED
- **Evidence:** duplicate **category** ids are rejected (`menu-sync-guard.ts:117-124`) but duplicates are not checked for **products** (`:129-150`) or **tables** (`:152-159`). Ids are validated for non-emptiness only, never for UUID shape (`:119`, `:130`, `:153`). `restaurant.businessType` is not validated at all and is written straight through (`api/menu/route.ts:181`, `:197`), while `theme` is rescued by `isMenuTheme` (`api/menu/route.ts:172`).
- **Impact:** a payload containing the same product id twice is accepted by the guard and then fails in Postgres — `ON CONFLICT DO UPDATE command cannot affect row a second time` (SQLSTATE 21000) — surfacing as `UPSERT_PRODUCTS` 500 (`api/menu/route.ts:332-334`), so a duplicated React key or a re-imported menu bricks publishing with no actionable error. A non-UUID id is passed to a uuid column and fails the same way; `businessType` junk is written raw.
- **Fix:** reject duplicate ids in all three arrays (small helper over `Set`), apply `UUID_RE`-style validation to every incoming id, and enum-check `businessType` against `BUSINESS_TYPES` (`constants.ts:35-43`).

### LIB-10 · Medium · `menu-sync-guard.ts` + `POST /api/orders` · VERIFIED
- **Evidence:** a table `token` is only required to be a non-empty string ≤128 chars (`menu-sync-guard.ts:157-158`); neither the guard nor the route checks for duplicate tokens within the payload, and migration 1002 creates no unique index on `restaurant_tables` (only `orders_daily_number_unique`, `orders_client_ref_unique`, `workers.session_token` — `1002_production_readiness.sql:96,109,149`). The order POST resolves the table with `.eq("restaurant_id", …).eq("qr_token", …).maybeSingle()` (`api/orders/route.ts:228-233`) and maps any error to 404 `BAD_TABLE`.
- **Impact:** if two table rows in one restaurant share a `qr_token`, `maybeSingle()` errors on >1 row and **every** order from those tables fails with "Table not found" — permanently, until the owner deletes and re-prints. The QR URL the app generates for both tables (`tables/page.tsx:25`) is then ambiguous. (Honest scope: honest use is safe — tokens come from 64 bits of `crypto.randomUUID` hex, `onboarding-store.tsx:73,435` — but the guard is the only thing standing between a buggy client and this state, and it does not check.)
- **Fix:** reject duplicate tokens in `validateSyncPayload`, and add `CREATE UNIQUE INDEX … ON restaurant_tables (restaurant_id, qr_token)` in the migration so the DB enforces it too.

### LIB-11 · Medium · `image-utils.ts` · VERIFIED
- **Evidence:** the passthrough decision uses pixel dimensions only — `if (longest <= MAX_DIM && PASSTHROUGH_MIME.has(file.type)) return file;` (`image-utils.ts:61`) — and PDF returns before any check at all (`:53`). The doc comment claims the branch keeps "uploads within the file-size cap" (`:50`). The decode step is `img.onerror = reject` (`:8`), where the rejection value is an `Event`, not an `Error` (`:5-11`), and the caller wraps everything in `catch {}` → `setErrorKey("ms_error_generic")` (`menu-scan-dialog.tsx:113-116`). `canvas.getContext("2d")!` is force-unwrapped (`:68`).
- **Impact:** (a) a 2048×2048 PNG screenshot (commonly 6–10 MB) passes through byte-for-byte, defeating the size cap and feeding the route's unbounded `req.formData()` (prior finding #4, `PERFORMANCE-OCR-REPORT.md:401`); (b) **HEIC/HEIF is not in `PASSTHROUGH_MIME`** (`:41`), so iPhone photos take the decode path, which only Safari can serve — `new Image()` fires `onerror` on Chrome/Firefox and the user gets the generic "something went wrong" with no hint that the format is unsupported; the same opaque failure covers a text file renamed to `.jpg`; (c) a missing 2-D context throws a `TypeError` instead of a domain error.
- **Fix:** check `file.size` in addition to the pixel test (and after compression), reject with a real `Error` inside the `onerror` handler, and give HEIC its own typed error (e.g. `HEIC_NOT_SUPPORTED`) that the dialog can map to a localized message; keep the PDF passthrough but bound its size too.

### LIB-12 · Medium · migration 1002 + `PUT /api/menu` + readers · VERIFIED
- **Evidence:** migration 1002 §4 adds `products.sort_order integer NOT NULL DEFAULT 0` plus `products_menu_order` for "PRODUCT ORDERING" (`1002_production_readiness.sql:122-140`), but nothing in the app ever writes it: the sync's product rows contain only `id, restaurant_id, category_id, name, description, price, image_url, image_source, is_available, updated_at` (`api/menu/route.ts:315-326`), `MenuSyncProduct` has no position field (`menu-mapping.ts:24-32`), and both readers order products by `created_at` (`api/menu/route.ts:78`, `menu/[slug]/[token]/page.tsx:34`). Categories have the full round trip by comparison (`menu-mapping.ts:21` for the field, written at `api/menu/route.ts:270`, read at `:73`).
- **Impact:** the advertised capability (owner-controlled dish ordering) is half-built: the column, index and backfill land in the DB and are then dead weight, and every product list is ordered by insertion time whatever the owner does. This is an existing, explicitly attempted capability with a missing writer, not a new feature.
- **Fix:** add `position` to `MenuSyncProduct` and `menuPayloadFromState` (`menu-mapping.ts:24-32`, `:114-122`), validate it like the category position, write `sort_order: p.position` in the product upsert (`api/menu/route.ts:315-326`), and switch both readers to `.order("sort_order", { ascending: true }).order("created_at", { ascending: true })`.

### LIB-13 · Medium · `utils.ts` + `menu-sync-guard.ts` · VERIFIED
- **Evidence:** `slugify` strips every non-`[a-z0-9]` character and falls back to the literal `"my-cafe"` (`utils.ts:17-25`), and it never truncates. The guard requires `^[a-z0-9-]{0,63}$` (`menu-sync-guard.ts:80`, tested at `:167`) with `SYNC_LIMITS.slugMax = 63` declared but unused (`menu-sync-guard.ts:18`). Slugs must be globally unique, enforced in-app with a 409 `SLUG_TAKEN` that aborts the whole sync (`api/menu/route.ts:222-231`).
- **Impact, in a TND/Arabic-first product:** (a) any restaurant whose name is entirely non-Latin (e.g. `مطعم`) slugifies to `""` → `"my-cafe"`; the **second** such restaurant can never publish a cloud menu — every save returns 409 and the owner has no way to see or change the slug; (b) any name producing >63 slug characters (the guard allows names up to 80, `SYNC_LIMITS.nameMax`) is rejected with `BAD_PAYLOAD` and likewise can never publish.
- **Fix:** make the slug collision-proof and bounded at the source — `slugify(name).slice(0, 56)` plus a short disambiguating suffix derived from the restaurant/owner id when the result is empty or already taken — and apply `SYNC_LIMITS.slugMax` as the single source of truth instead of duplicating `63` in the regex.

### LIB-14 · Low · `owner-auth.ts` · VERIFIED
- **Evidence:** `authBypassEnabled()` requires `process.env.NODE_ENV !== "production"` **and** `SUFRA_AUTH_DISABLED === "1"` (`owner-auth.ts:28-39`). Call sites are exclusively server-side: `getOwnerSessionForRsc` (`:186`), `getOwnerSessionForRequest` (`:200`), `getWorkerSession` (`worker-auth.ts:86`), `requireWorkerSessionForRsc` (`worker-auth.ts:92`). No `NEXT_PUBLIC_*` variable carries the flag. Prior-art correction: `PERFORMANCE-OCR-REPORT.md:402` claims `SUFRA_AUTH_DISABLED=1` is live in `.env.local` — **there is no `.env.local` in this checkout** (only `.env.example`, where the variable is commented out and documented as dev-only).
- **Impact:** no production deployment built and started normally can enable the bypass, so this is not a live vulnerability. Residual: `NODE_ENV` is read at runtime on the server, so a custom server started as `NODE_ENV=development node server.js` against a production build would honour the flag; a build-time constant would remove the question entirely.
- **Fix:** none required for correctness; if you want it airtight, gate on a build-injected constant (e.g. `process.env.__SUFRA_BUILD_ENV`) rather than the runtime `NODE_ENV`. Do not "harden" this by deleting the bypass — it is the only way to run the app without Supabase credentials (see Open questions).

### LIB-15 · Low · `PATCH /api/orders/[id]` (owner branch) · VERIFIED
- **Evidence:** for a worker session the route correctly ignores the body and writes the session's own `workerId`/`fullName` (`[id]/route.ts:98-100`). For an owner session it accepts `body.acceptedBy` after a UUID shape check only (`:101-105`) — no lookup that the worker belongs to `order.restaurant_id`. Migration 1002 adds `accepted_by uuid` with no FK (`1002_production_readiness.sql:116`), so nothing rejects a foreign id either.
- **Impact:** an owner-initiated accept can stamp an arbitrary (including another restaurant's) worker id onto the order, corrupting the "who accepted this" label the dashboards display (`api/orders/route.ts:30-31`). Not a privilege escalation; a data-integrity defect that only an owner can trigger.
- **Fix:** resolve the id with `.from("workers").select("id").eq("id", body.acceptedBy).eq("restaurant_id", order.restaurant_id).maybeSingle()` and 400 on miss; add the FK once the schema exists.

### LIB-16 · Low · `worker-auth.ts` · VERIFIED
- **Evidence:** the live worker cookie is set with `httpOnly/sameSite:"lax"/secure: NODE_ENV === "production"/path/maxAge` (`api/auth/worker/accept/route.ts:130-136`) — correct. The string helpers in the lib do not match it: `serializeWorkerSessionCookie` omits `Secure` (`worker-auth.ts:119-121`) and `grep` shows **no caller at all** (dead); `clearWorkerSessionCookie` also omits `Secure` (`:123-125`) and *is* used by the logout route (`api/auth/logout/route.ts:7`).
- **Impact:** today's impact is ~nil (a `Max-Age=0` deletion over plain HTTP is harmless, and the dead helper is never wired). The risk is a future caller adopting `serializeWorkerSessionCookie` as "the" cookie serializer and silently dropping `Secure` on the real session cookie. The owner-side serializer (`owner-auth.ts:215-221`) is a different, correct implementation — two live conventions for the same job.
- **Fix:** delete `serializeWorkerSessionCookie` and have `clearWorkerSessionCookie` delegate to `res.cookies.set(..., { httpOnly:true, sameSite:"lax", secure: NODE_ENV==="production", maxAge:0 })`, so one convention exists.

### LIB-17 · Low · `qr.ts` · VERIFIED
- **Evidence:** `toQrDataUrl` is deterministic for a given value (fixed options, `qr.ts:3-12`), but `downloadQrPng` attaches only `.then` with no `.catch` (`:14-23`), and `downloadAllQrPngs` paces the loop with a fixed `setTimeout(350)` instead of awaiting the download (`:25-32`).
- **Impact:** an encoding failure becomes an unhandled promise rejection with no user-visible error — the user clicks "download all" and gets nothing. For a 60-table restaurant the loop runs ~21 s of sleeps, and browsers throttle/block multiple automatic downloads ("Download multiple files?" prompt); if the prompt is dismissed the loop keeps "succeeding" and silently skips the rest. (Token/URL generation is **not** in this module — see Verified-working for the collision analysis on the real token sources.)
- **Fix:** `await toQrDataUrl(...)`, catch and surface an error toast, and drive the loop from the resolved data URL (or yield until the anchor click is observed) rather than a fixed sleep; a ZIP built server-side would remove the prompt entirely.

### LIB-18 · Low · `utils.ts` · VERIFIED
- **Evidence:** `makeToken` generates 8 random bytes and then `Array.from(bytes, b => b.toString(36)).join("").slice(0, 8)` (`utils.ts:27-33`). Base-36 encodings are 1 character for `b < 36` and 2 otherwise (expectation 1.86 chars/byte), so the first 8 characters are determined by roughly the first 4–5 bytes and the tail bytes are discarded. Enumerating the reachable 8-character strings by dynamic programming over the length distribution gives exactly `36·A(7) + 220·A(6) = 7,533,096,560,896 ≈ 2^42.8` possibilities.
- **Impact:** the helper's comment ("must still be unpredictable", implying 8 bytes = 64 bits) overstates the entropy by ~21 bits. Real-world impact is limited because the only caller is the offline/demo invite fallback (`invite-dialog.tsx:80`) — the security-relevant tokens are server-minted (`worker-invite.ts:7-14`, used at `api/auth/worker/invite/route.ts:52`) and table tokens come from `crypto.randomUUID()` hex (`onboarding-store.tsx:73,435`). A ~42-bit space still has no realistic collision at this scale.
- **Fix:** keep all 64 bits — `Array.from(bytes, (b) => b.toString(16).padStart(2, "0")).join("")` — or delete the helper if the demo path does not need it.

### LIB-19 · Low · `utils.ts` + `menu-sync-guard.ts` · VERIFIED
- **Evidence:** the guard accepts any 3–8 digit hex colour (`/^#[0-9a-fA-F]{3,8}$/`, `menu-sync-guard.ts:171`), but `hexToRgba` returns the white fallback unless the value is exactly 6 digits (`utils.ts:10`), and `colorFromHex` feeds the same string to it for the accent background (`menu-mapping.ts:61-75`).
- **Impact:** a `#abc` or `#11223344` brand colour passes validation, then renders a **white** translucent accent behind the brand elements with no error — a visible theme bug that the validator explicitly allowed.
- **Fix:** tighten the guard to `^#[0-9a-fA-F]{6}$` (the palette and the pickers all emit 6 digits) or expand `hexToRgba` to handle the 3-digit short form.

### LIB-20 · Low · `rate-limit.ts` · VERIFIED
- **Evidence:** `rateLimitDisabled()` returns true for `SUFRA_RATE_LIMIT_DISABLED ∈ {"1","true"}` with no environment guard (`rate-limit.ts:36-39`), unlike `authBypassEnabled` which requires a non-production `NODE_ENV` (`owner-auth.ts:28-31`).
- **Impact:** a stray value in a production `.env` (the file is copied from `.env.example`, which documents the switch next to the auth bypass) silently removes throttling from login, recover, reset, order creation, scan and upload. Config-only, but the asymmetry with the auth bypass is the wrong default.
- **Fix:** require `process.env.NODE_ENV !== "production"` for the override, or log a loud warning as `authBypassEnabled` does.

### LIB-21 · Low · `worker-auth.ts` · VERIFIED (FK consequence INFERENCE)
- **Evidence:** `requireWorkerSessionForRsc` is exported with the docstring "Server-component guard" (`worker-auth.ts:91-96`) and has **no caller** — the worker dashboard layout deliberately does no server check, documenting that enforcement lives in `WorkerShell` (`/api/auth/worker/me`) and the APIs (`(worker)/worker/dashboard/layout.tsx:4-8`), which `GET/PATCH /api/orders` do (401 without a session, `api/orders/route.ts:36-39`). In bypass mode `getDevWorkerSession` returns the fixed `workerId: "00000000-0000-4000-8000-000000000000"` (`worker-auth.ts:112`), which the accept path then writes to `orders.accepted_by` (`[id]/route.ts:99`).
- **Impact:** dead code that advertises a control the app decided not to use (delete or wire it — leaving it invites a future layout to add a redundant, bypass-sensitive guard). In bypass mode the accept path writes a sentinel worker id that exists in no table: `accepted_by` has no FK today (`1002_production_readiness.sql:116`) so it stores silently and the dashboards show a worker that cannot be resolved; **if an FK is added later, dev-mode accept will start failing with a 23503 [INFERENCE]**.
- **Fix:** delete `requireWorkerSessionForRsc` (or use it in the worker layout, which would then need an offline escape hatch), and in the dev session use the real worker row (or skip the `accepted_by` write when the id is the sentinel) so dev and prod paths agree.

### LIB-22 · Low · `order-utils.ts` · VERIFIED
- **Evidence:** `computeOrderTotal([])` returns `0` — the loop body never runs, `Math.round(0*100)/100 === 0`, and the range check is `total > MAX_ORDER_TOTAL || total < 0` (`order-utils.ts:166-181`). No test covers the empty list; the route cannot reach it because `orderBodySchema.items` requires ≥1 (`order-utils.ts:71-74`).
- **Impact:** a free (0-priced) catalog product produces an order whose total is 0 and which passes every guard, including the range check. Not exploitable on its own, but "total must be ≥ 0" is not a business rule anyone wrote down, and the empty-list case silently produces a valid-looking order.
- **Fix:** decide the contract explicitly — reject `items.length === 0` and `total <= 0` in `computeOrderTotal` (or document that zero-value orders are intended) and add the empty-list case to the test file.

### LIB-23 · Medium · `order-utils.ts` (dead export with live tests) · VERIFIED
- **Evidence:** `nextOrderNumberFor` is exported and covered by two tests (`order-utils.test.ts:220-233`) but has **no production caller** — `grep` shows the only reference outside the test is its own definition. The real allocator inlines the same formula: `(currentMax ?? 1000) + 1` (`api/orders/route.ts:108-116`).
- **Impact:** the tested contract and the executed contract are different code. The per-line-qty regression the test was written to lock down (its own comment cites the legacy `?? 1000 + 1` precedence bug) can be reintroduced in `allocateOrderNumber` with the suite still green. This is the concrete instance of the coverage gap below.
- **Fix:** have `allocateOrderNumber` call `nextOrderNumberFor(currentMax)` so the tested function is the executed one (preferred), or delete the helper and move the assertions onto the route.

### LIB-24 · Medium · `utils.ts` (`appBaseUrl`) · VERIFIED
- **Evidence:** `appBaseUrl()` is `typeof window !== "undefined" ? window.location.origin : "https://sufra.app"` (`utils.ts:36-38`) — it never reads `NEXT_PUBLIC_APP_URL`, although that variable is a first-class setting (`.env.example`: `NEXT_PUBLIC_APP_URL=http://localhost:3000`, and `NEXT_PUBLIC_` is inlined into the client bundle, so it is available in both environments). The password-recovery route already implements the correct resolver locally — configured URL else `new URL(req.url).origin` (`api/auth/recover/route.ts:10-14`) — so two conventions for the same job exist. All three `appBaseUrl()` call sites are `"use client"` components (`(owner)/dashboard/tables/page.tsx:1,24-25`, `(owner)/dashboard/workers/page.tsx:1,64`, `components/dashboard/invite-dialog.tsx:1,52-55`), which are still **server-rendered on first paint**.
- **Impact:** (a) on the server-rendered first paint `typeof window` is undefined, so the initial HTML contains the hardcoded placeholder domain `https://sufra.app/menu/<slug>/<token>`; a user who copies the visible URL text before hydration copies a foreign domain, and React logs a text-content hydration mismatch when it corrects the value. (b) The production value is always `window.location.origin`, which is *not* the canonical app URL whenever the app is reached through another host — a Vercel preview alias, a self-hosted `http://<ip>:3000`, or a reverse proxy — so QR codes and invite links generated there point at an ephemeral/unreachable origin, while the configured `NEXT_PUBLIC_APP_URL` (the only value the deployer can control and the one the recovery mail already uses) is ignored. Password reset itself is **not** affected because it uses its own `appBase(req)`.
- **Fix:** make `appBaseUrl()` prefer `process.env.NEXT_PUBLIC_APP_URL` (trailing-slash-trimmed) and fall back to the window origin, and return that configured value — never a hardcoded third-party domain — when there is no window; then delete the duplicated `appBase()` in the recover route so a single resolver exists. This keeps SSR and client values identical (no hydration mismatch) and makes printed QR codes follow the deployer's canonical domain.

### LIB-25 · Low · `worker-invite.ts` + invite readers (fail-open TTL) · VERIFIED
- **Evidence:** the TTL is set on insert (`expires_at: new Date(Date.now() + INVITE_TTL_MS).toISOString()`, `api/auth/worker/invite/route.ts:58`) but both readers treat a **null** `expires_at` as still valid: the reject condition is `!invite || invite.is_used === true || (invite.expires_at && new Date(invite.expires_at).getTime() < Date.now())` (`api/auth/worker/accept/route.ts:63-67`, same shape at `api/auth/worker/invite/[token]/route.ts:29`). With `expires_at` null the third clause is falsy, so the invite passes. The migration's own comment records that `worker_invites` is part of the **pre-existing** live schema (`1002_production_readiness.sql:143-146`), i.e. rows this app did not insert.
- **Impact:** any invite row whose `expires_at` is null — pre-existing rows, or any future writer that omits the column — is a credential with an infinite lifetime; combined with LIB-02 (sessions also never expire server-side) nothing in the worker path ever ages out. Today's own writer always sets the column, so the exposure is latent, not live.
- **Fix:** invert the default — require an explicit future timestamp to accept (`if (!invite || invite.is_used === true || !invite.expires_at || new Date(invite.expires_at).getTime() < Date.now())`) and add `NOT NULL DEFAULT now() + interval '24 hours'` (plus a backfill for null rows) in the migration.

## Verified-working

- **Pricing is genuinely server-computed.** Catalog lines reject any extra key (`.strict()`, `order-utils.ts:21-32`; tests at `order-utils.test.ts:31-73`); a top-level `total`/`status`/`isPaid` is stripped (`order-utils.ts:76`) and the recorded total comes from `priceLines` → `computeOrderTotal` (`api/orders/route.ts:171-178`), never from the body. A missing or unavailable product is a hard 404/409, not a silently-priced line (`api/orders/route.ts:154-164`).
- **The per-line and per-order clamps are real and layered:** `qty ∈ [1,50]`, `≤60` lines, `≤500` total qty, `price ≤ 999_999.99` per unit and a finite `total ≤ 10_000_000` with a 422 on overflow (`order-utils.ts:12-17,74,146`, `api/orders/route.ts:176-178`).
- **Cross-restaurant IDOR is closed** on menu sync: foreign and orphaned ids are rejected before any upsert (`findConflicts`/`findSyncConflicts`, `menu-sync-guard.ts:49-68`; queried with `restaurant_id.neq.X OR restaurant_id IS NULL`, `api/menu/route.ts:29-43`), every delete is re-scoped to the restaurant (`:291-309`, `:345-351`, `:378-384`), and the slug clash check runs before writes (`:222-231`). Orphan categories cannot be created: every product's `categoryId` must be in the payload's category set (`menu-sync-guard.ts:135-136`).
- **Rate-limit boundary arithmetic is correct** (`rate-limit.ts:57-67`) — strictly-inside-window retention and a correct time-to-oldest retry-after; call sites gate login, recover, reset, order creation, scan, upload and worker-accept before doing any work (`api/auth/*/route.ts`, `api/orders/route.ts:192`).
- **Worker identity is never taken from client input:** `getBearerToken` accepts only `Bearer`, `getSessionToken` prefers it over the cookie and rejects lookalike names, and both are pure-parsed with no body/query fallback (`worker-auth.ts:31-57`, tested). `PATCH` overwrites `accepted_by`/`accepted_by_name` from the verified session (`[id]/route.ts:98-100`), and an unknown DB role degrades to the least-privileged `Cashier` (`:75`, `normalizeStaffRole` → null → `?? "Cashier"`).
- **Cashier cannot mark paid** — the one enforced cell of the matrix: `wantsPaid` covers both `status:"paid"` and `isPaid:true` and 403s for Cashier (`[id]/route.ts:76-79`); `status:"paid"` is correctly translated to `is_paid` because the table's status domain is pending/accepted only (`:83-86`).
- **Secrets are CSPRNG and server-minted:** invite tokens are `randomBytes(16).toString("hex")`, session secrets `randomBytes(32)`, with a 24 h `expires_at` set at mint time and enforced on read (`worker-invite.ts:4-14`, `api/auth/worker/invite/route.ts:52-58`, `accept/route.ts:59-66`); the client cannot choose either value (`invite-dialog.tsx:71-82` only falls back to `makeToken` offline). One-time use is claimed by a conditional update (`accept/route.ts:120`).
- **Cookie flags on the two live session paths are correct:** owner `httpOnly + sameSite:"lax" + secure (prod) + path:"/" + maxAge` (`owner-auth.ts:215-221`, applied at login/callback/reset), worker identical (`accept/route.ts:130-136`). The owner cookie value is a compact base64url JSON with a tolerant parser that returns `null` on garbage (`owner-auth.ts:80-98`), and the access token is re-verified against Supabase on every request, so a tampered cookie cannot mint a session.
- **Dev bypass cannot fire in production and does not trust client identity:** see LIB-14 (`owner-auth.ts:28-39`) and LIB-21 — both dev sessions resolve their restaurant from the DB (`owner-auth.ts:45-60`, `worker-auth.ts:102-117`), so no bypassed route reads identity from the request.
- **QrImage never renders an empty QR:** every call site passes a non-empty value (table token URL at `tables/page.tsx:114`, `table-card.tsx:34`; the invite QR is behind `{token ?}` at `invite-dialog.tsx:151-164`), and generation runs in an effect with a cleanup guard (`qr-image.tsx:18-26`), so no SSR/hydration mismatch or unhandled rejection from an empty string.
- **`isMenuTheme` is enforced where the DB is written** (`menu/route.ts:172` → `menu_layout_theme: theme`), so an arbitrary client theme string cannot reach the column.
- **`format.ts`** renders TND at millime precision with `Intl` (3 fixed decimals, `format.ts:1-8`); `constants.ts` is a pure type/data module with no browser APIs (`constants.ts:1`), so it is safely importable from server components.

## Open questions

1. **Can `owner-auth.ts` even be exercised here?** With no `.env.local` and no Supabase project, `supabaseAdmin` is null and every session path returns `null`/`EMPTY`. Any fix to LIB-02/LIB-03 is unverifiable end to end until the base schema and credentials exist — and note the dev bypass is currently the *only* way to run the app at all, so it should not be removed to "harden" the audit.
2. **Is millime precision (LIB-04) a hard requirement, or is 2-decimal TND intended?** `formatDT` and the OCR import both say 3; `order-utils` says 2. Only the product owner can settle which one the invoice must match.
3. **Is `products.sort_order` (LIB-12) intended to become owner-editable, or was the migration speculative?** If speculative, the column/index/backfill should be dropped from the migration rather than wired.
4. **What is the sanctioned client-IP source** for the limiter (LIB-08)? The fix depends on the deployment target (Vercel vs the bundled `docker-compose.yml` + nginx), and no proxy config in this repo appends a trusted hop.
5. **Should reopening an accepted order be allowed at all** (for a mis-tap), and if so by which roles (LIB-01)? The row-level answer changes whether the fix is a 403 or a role gate.
6. **`OrderStatus` includes `"paid"` (`constants.ts:107`) while the DB status domain is pending/accepted** and payment is the `is_paid` flag. The dual representation works today only because PATCH special-cases `status:"paid"` (`[id]/route.ts:83-86`); it is unclear whether any other consumer round-trips that local-only value, and the routes slice should confirm.

# Frontend / UX Audit

## Verdict

The rendering layer is competently built — the guest menu, the owner dashboards and the onboarding wizard all render, are dark-theme-consistent, i18n'd and mostly free of frozen spinners. But the surface is not operational for a first customer, because the two flows that matter are broken end to end: the landing page's primary CTA (`/onboarding`) is unauthenticated and silently discards everything the owner builds while reporting "Saved locally", and the owner working dashboard remains in local-demo mode after a client-side sign-in, so it shows zeros instead of real orders. On the guest side the menu renders correctly but the order submission is not idempotent (a fresh `clientRef` per attempt defeats the server's duplicate guard) and neither the cart nor the confirmation survives a refresh. Worker access is guarded client-side only and that guard is defeated by a writable `localStorage` key. Nothing here is blocked by the missing base schema specifically — this slice would fail with a perfect database, since the defects are in state ownership, error surfacing and navigation.

## Required behaviour

Derived from the code and its own comments (`src/components/dashboard/worker-shell.tsx:18-21`, `src/app/api/menu/route.ts:221`, `src/lib/use-orders.ts:12-19`):

1. A guest may scan a per-table QR, browse the live menu, add to cart, submit once, and see a confirmation. Repeating a submit must not create a second order; a refresh must not lose the cart or the order number.
2. Any failure of a submit must tell the guest *what* failed in terms they can act on (which item is gone, retry in N seconds, retry later) — never a dead end.
3. The owner's dashboard must reflect server state within one poll after sign-in, with no hard refresh required.
4. The owner must be told, unambiguously, whether the menu is published; a menu that never reached the server must never be presented as live and must never yield printable QR codes.
5. Worker access to `/worker/**` must be denied without a server-validated session; a client-writable key must never confer a role.
6. Every write path (`POST /api/orders`, `PATCH /api/orders/:id`, `PUT /api/menu`) must surface its own failure to the operator: an in-flight control is disabled, a failed request produces a visible, specific error, and an optimistic update is reverted when the server refuses.
7. State that the user must be able to rely on across a reload (cart, order number, worker identity, saving status) must be persisted or explicitly declared ephemeral in the UI.
8. Underlying all of the above: no page may render an interactive authenticated surface without a session, and no route may be reachable only by hand-typing its URL.

## Findings

### FE-01 · Critical · Onboarding wizard · VERIFIED
- Evidence: `src/app/onboarding/page.tsx:1` is `"use client"` and `:165-167` renders `<WizardInner />` with no session check; the route is reached from the landing page's only CTAs (`src/app/page.tsx:117, 169, 316`). Autosave fires unconditionally after any change (`src/lib/onboarding-store.tsx:252-270`), `PUT /api/menu` answers `401 {error:"UNAUTHORIZED"}` without an owner session (`src/app/api/menu/route.ts:140-143`), `saveNow` maps that to `"local"` (`src/lib/onboarding-store.tsx:240-244`), and `SaveStatus` renders `save_local` = "Saved locally" (`src/components/dashboard/save-status.tsx:11-18`, `src/lib/i18n.tsx:127`). No `auth/signup` or `auth/login` link appears anywhere in `src/app/onboarding` or `src/components/onboarding` (verified by grep).
- Impact: a first customer clicks the hero CTA, builds an entire menu, sees "Saved locally" (which reads as success), and none of it ever leaves the browser. There is no account, no restaurant row, no prompt to create one. The only persisted copy is `localStorage["sufra.menu.sync"]` on that one device (`:214-222`), and the wizard's own final step hands them a dead URL (FE-10). This is the main funnel of the product, and it terminates in silence.
- Fix: make `/onboarding` server-guarded — `const session = await getOwnerSessionForRsc(); if (!session) redirect("/auth/signup?next=/onboarding");` — or, if anonymous drafting is intended, gate the CTA on `isCloud`, replace the "Saved locally" status with "Not published — create an account" and add a signup action on the final step.

### FE-02 · Critical · SaveStatus / onboarding-store · VERIFIED
- Evidence: `src/components/dashboard/save-status.tsx:11-18` returns early on `!isCloud` and renders the "Saved locally" pill, so the `"error"` branch (`:35-41`) is unreachable while `isCloud` is false. `isCloud` is `restaurantId !== null` (`src/lib/onboarding-store.tsx:533`) and `restaurantId` is only set by the mount fetch (`:159`) or a successful PUT (`:234`) — so on the *first* save it is necessarily null. The first save is exactly the one that can fail with `409 SLUG_TAKEN` (`src/app/api/menu/route.ts:209-211, 229-231`) or `500 INSERT_RESTAURANT`, both of which `saveNow` maps to `"error"` (`:239-245`) — a state the UI can never show.
- Impact: the owner's very first publish fails (slug collision with another restaurant, or any 5xx), the screen says "Saved locally" in neutral grey, and the owner proceeds to print table QR codes (`src/app/(owner)/dashboard/tables/page.tsx:27-48`) for a restaurant that does not exist in the database. Every guest who scans gets a 404. The failure is unrecoverable from the UI: the slug is derived from the restaurant name (`src/lib/menu-mapping.ts:100`) and is not editable anywhere.
- Fix: render the failure state independently of `isCloud`; surface `result.error` and distinguish `SLUG_TAKEN` from a transport error; expose the slug in `/dashboard/settings` and let the owner change it, with a retry.

### FE-03 · High · Guest menu — order submit · VERIFIED
- Evidence: `src/components/guest-menu.tsx:119-131` builds the POST body with `clientRef: crypto.randomUUID()` computed *inside* `submitOrder`. The server deliberately uses `client_ref` as its idempotency key: it writes it (`src/app/api/orders/route.ts:272`) and, on a `23505` unique violation, looks the order up by `(restaurant_id, client_ref)` and returns the existing order (`:368-404`).
- Impact: the duplicate-order protection is defeated by the client, because every attempt carries a new key. Repro: on flaky mobile data, tap "Send order", watch the request time out client-side while the server commits it, get the "Network error" toast (`:144-145`), tap "Send order" again → the guest is charged twice at the counter for two identical orders, on two different order numbers. This is the single most expensive failure mode in the product.
- Fix: mint the `clientRef` once per cart (e.g. `const clientRef = useRef(crypto.randomUUID())`), reuse it across retries, and regenerate it only after a confirmed `res.ok && data.cloud`.

### FE-04 · High · Guest menu — 409/404 on submit · VERIFIED
- Evidence: `src/components/guest-menu.tsx:132-143` shows one generic toast using `data.message`. The server's messages are `"Some items are no longer available."` (409) and `"Some items are no longer on the menu."` (404) (`src/app/api/orders/route.ts:156-159`) and carry **no product identifiers**. The rendered menu comes from a server render that filtered `is_available = true` at page load (`src/app/menu/[slug]/[token]/page.tsx:39`, `:57-65`), and nothing re-fetches, so an item that went unavailable mid-session is still listed, still addable, and still in the cart.
- Impact: the guest is told to change something but has no way to learn what; the cart retains the offending line. The only recoveries are to guess item-by-item or reload the page — and reloading destroys the cart (FE-05). Guests in this state abandon the order.
- Fix: include the offending `productIds` in the 409/404 body; on receipt, mark those rows unavailable in local state, drop them from the cart, and toast a specific, named list. Add a "refresh menu" action.

### FE-05 · High · Guest menu — cart and confirmation durability · VERIFIED
- Evidence: `cart`, `cartOpen`, `submitting` and `confirm` are plain `useState` in `src/components/guest-menu.tsx:59-62`. Nothing is written to `sessionStorage`/`localStorage`. The success path sets `confirm` (`:134`) and the confirmation overlay (`:565-588`) offers only "Back to menu" (`:578-585`). Guests cannot read `/api/orders` — it is owner/worker-only (`src/app/api/orders/route.ts:38-40`).
- Impact: (a) any refresh, accidental back-swipe or phone lock-screen eviction wipes an in-progress cart with no warning; (b) the order number and total — the guest's only proof and the only way to reconcile at the counter — exist for exactly one render and are gone forever after a refresh. There is no "my order" view.
- Fix: persist `{cart, confirm}` to `sessionStorage` under a key scoped to `slug + token`, rehydrate on mount, and keep the confirmation retrievable for the session (e.g. a persistent bar with "Order #12 · sent").

### FE-06 · High · Worker invite accept / invite create · VERIFIED
- Evidence: `src/app/(worker)/worker/invite/[token]/page.tsx:127-144` treats only `401`/`404` as rejections; the comment at `:141` states that `"429/503 and network failures degrade to the local demo path"`. That path runs `createInvite(role, token)` + `acceptInvite(token, cleanName)` (`:155-158`), which writes a fabricated worker into `localStorage["sufra.worker"]` (`src/lib/onboarding-store.tsx:496-523`, `:115-123`) and then pushes `/worker/dashboard` (`:164`). The mirror defect exists on creation: `src/components/dashboard/invite-dialog.tsx:73-83` shows the 401 message but converts *every other* failure (403/429/500/network) into a silently minted local invite link (`:80-83`) presented as a normal QR (`:50-56`).
- Impact: under rate limiting or a broken backend, the owner hands out a link that yields a worker device holding no server session, and that device's order board is permanently empty (see FE-08). The worker is shown a working terminal UI — "Cashier" badge, "New order" button, working accept buttons — while every request 401s. Nobody is told the invite was never real.
- Fix: restrict the local fallback to genuinely-offline conditions (`fetch` rejects, or `503 NO_BACKEND`) and label it in the UI ("Demo mode — not connected"); for 429/5xx show the error and a retry. Do not write a worker session on a path where the server explicitly refused.

### FE-07 · High · WorkerShell / worker dashboard layout · VERIFIED
- Evidence: `src/components/dashboard/worker-shell.tsx:22-51` is the only gate. It runs once (`[]` deps with `eslint-disable-next-line react-hooks/exhaustive-deps` at `:50`) and only bounces when `res.status === 401 && !workerSession` (`:40-42`). `workerSession` is restored from `localStorage["sufra.worker"]` on mount with a `typeof w.id === "string"` check and nothing else (`src/lib/onboarding-store.tsx:103-113`, key defined at `:34`), and it is written by the client itself (`:115-123`). Once it is truthy the redirect is skipped permanently. The layout documents the omission on purpose (`src/app/(worker)/worker/dashboard/layout.tsx:4-9`). With `isCloud` false the page renders the local store and a working "New order" dialog (`src/app/(worker)/worker/dashboard/page.tsx:116-119, 177`) and a role-driven button gated purely on the localStorage role (`:95`, `canMarkPaid = workerSession?.role === "Manager"`).
- Impact: repro — in any browser, `localStorage.setItem("sufra.worker", '{"id":"x","name":"x","role":"Manager"}')`, then open `/worker/dashboard`. You get a fully interactive manager terminal (Mark-paid buttons included) with no session of any kind. Real order data stays protected by the PATCH/GET guards, but the app presents a fake operational UI as authenticated, and the role that drives the UI is client-written. The `!workerSession` check also races the provider's own restore effect, so the 401 bounce is non-deterministic depending on effect ordering.
- Fix: make the check unconditional — bounce on any non-`ok` response and on `401` regardless of localStorage; treat `localStorage["sufra.worker"]` as a display cache only, never as authorization, and clear it when `/api/auth/worker/me` fails. The durable fix is a server guard in `src/app/(worker)/worker/dashboard/layout.tsx` reading the worker cookie (`getWorkerSession` on a request-scoped cookie) the way the owner layout already does.

### FE-08 · High · useOrders / onboarding hydration · VERIFIED
- Evidence: `src/lib/onboarding-store.tsx:126-204` is a mount-only (`[]` deps) `GET /api/menu` that sets `restaurantId` (`:159`) and therefore `isCloud` (`:533`); the only other assignment is a successful PUT (`:234`). `src/lib/use-orders.ts:21-55` derives everything from `live = isCloud`: when false it mirrors the local store (`:26-28`) and when true it polls `/api/orders` every 3 s (`:31-55`). Sign-in uses `router.replace("/dashboard")` + `router.refresh()` (`src/components/auth-form.tsx:39-40`) — a client navigation that preserves the provider, so the mount effect does not re-run; `router.refresh()` re-renders server components without remounting client providers. The worker path is identical: the invite page pushes `/worker/dashboard` (`src/app/(worker)/worker/invite/[token]/page.tsx:164`) after the provider already fetched once without a session.
- Impact: an owner who signs in sees the Overview with zero revenue, zero orders and empty charts (`src/app/(owner)/dashboard/page.tsx:55-63`) even though the restaurant has live orders; `/dashboard/orders` shows the empty state with the *demo* copy (`src/app/(owner)/dashboard/orders/page.tsx:78-84`). A worker pushed to `/worker/dashboard` after accepting an invite sits in front of a board that will never update. Both are fixed only by a manual full page reload, which no user will think to do. `SaveStatus` additionally shows "Saved locally" (`src/components/dashboard/save-status.tsx:11`), so the owner may start re-entering existing data.
- Fix: derive `isCloud` from an authoritative session call (`GET /api/auth/session`, which already exists: `src/app/api/auth/session/route.ts`) and re-hydrate when auth changes, or replace the post-login client navigation with `window.location.assign("/dashboard")` so the provider remounts.

### FE-09 · High · Navigation / landing page · VERIFIED
- Evidence: grepping `"/auth/login"` and `href="/auth` across `src/app` and `src/components` yields only `(owner)/dashboard/layout.tsx:8` (redirect), `owner-shell.tsx:73` (sign-out), `auth-form.tsx:125,137,144` and `forgot-form.tsx:74` (cross-links between auth pages). The landing page header (`src/app/page.tsx:100-121`) and hero CTA (`:168-181`) and the bottom CTA (`:315-322`) all point exclusively at `/onboarding`; the wizard's own header links only to `/` (`src/components/onboarding/navbar.tsx:31`), and no link to `/auth/signup` exists in the onboarding tree.
- Impact: a returning owner who opens the site root has no discoverable way back into their dashboard — they must hand-type `/auth/login`. If they instead follow the CTA (as everything invites them to), they walk the whole wizard and only reach `/dashboard` through step 5 → "Finish" (`src/components/onboarding/step-preview.tsx:195-201`); that route is server-guarded, so an anonymous user is bounced to `/auth/login` with no `next` parameter and no explanation. The sign-in page is effectively unlinked.
- Fix: add a "Sign in" action to the landing header; have the wizard's final CTA route to `/auth/signup?next=/onboarding`; preserve `next` through the login redirect.

### FE-10 · Medium · StepPreview — scan URL · VERIFIED
- Evidence: `src/components/onboarding/step-preview.tsx:44` builds `${restaurantName → slug}.menuos.app` and `:128-131` renders `https://<slug>.menuos.app` next to a copy button (`:132-143`). The real guest URL is `<origin>/menu/<slug>/<table token>`, built correctly elsewhere with `appBaseUrl()` (`src/app/(owner)/dashboard/tables/page.tsx:24-25`, `src/lib/utils.ts:36-38`), and the route lives at `src/app/menu/[slug]/[token]/page.tsx`. No `menuos.app` domain appears in any config or env reference.
- Impact: the wizard's "Scan link" — the one URL the owner is invited to copy and share — points at a domain the product does not own and a path the guest route does not serve. The copy button reports success unconditionally (`handleCopy` never checks `navigator.clipboard` and has no failure branch).
- Fix: build the displayed and copied URL from `appBaseUrl()` plus the real route, using an actual table token, or label it as "menu preview" and point at `/menu/<slug>`.

### FE-11 · Medium · StepPreview / onboarding Navbar / Tables page · VERIFIED
- Evidence: `src/components/onboarding/step-preview.tsx:118-121` renders `prv_ready` ("Live") unconditionally, including for a wizard that has never reached the server; `handleFinish` (`:35-41`) only sets local state and shows a success toast — it never calls `saveNow()`. `src/components/onboarding/navbar.tsx:75-80` labels a button "Publish" (`ob_publish`) that merely jumps to step 5 via `onGoToFinalStep`. `src/app/(owner)/dashboard/tables/page.tsx:27-33` toasts success the moment `generateTables(n)` mutates local state, and `:35-48` downloads/prints QR PNGs without ever consulting `savingState` or `isCloud`.
- Impact: combined with FE-02, an owner whose first PUT failed still sees "Ready", still gets a "generated" toast and still gets a printable sheet of QR codes for a restaurant that does not exist. The menu itself is always written with `isPublished: true` (`src/lib/menu-mapping.ts:107`), so "published" is not a state the user controls — the badge claims a fact the UI never verified.
- Fix: drive the badge from `isCloud && savingState === "saved"`; make `handleFinish` await `saveNow()` and only then show success; disable QR download/print while `!isCloud || savingState === "error"` with an inline reason.

### FE-12 · Medium · Onboarding autosave · VERIFIED
- Evidence: `src/lib/onboarding-store.tsx:252-270` is a 900 ms debounce with a `clearTimeout` cleanup and nothing else; no `pagehide`/`beforeunload`/`visibilitychange` flush exists, and there is no unmount flush. The localStorage snapshot is written *inside* `saveNow` (`:214-222`), so it too only happens after the debounce elapses.
- Impact: repro — on `/onboarding`, type a category name, then within 900 ms close the tab (or, on the owner menu editor, navigate to another route that unmounts the editor). The change is never PUT and never even reaches the local snapshot; the owner's typing silently disappears. On mobile the same happens on a phone call or app switch.
- Fix: flush on `pagehide`/`visibilitychange` — write the local snapshot synchronously and fire the PUT with `navigator.sendBeacon` (or `fetch(..., {keepalive:true})`) — and shorten or bypass the debounce when the document is hidden.

### FE-13 · Medium · useOrders / WorkerNewOrderDialog / store hydration · VERIFIED
- Evidence: (a) `src/lib/use-orders.ts:36-47` — `if (!res.ok) return;` followed by an empty `catch`, inside a 3 s interval (`:50`), so a 401/500 leaves the last-known list rendered indefinitely with no banner, no error and no retry; (b) `src/components/dashboard/worker-new-order.tsx:104-131` has **no `catch` block at all**, only `finally` — a non-JSON error body (an HTML 429/500 page, or a proxy error) makes `res.json()` reject, the rejection escapes `place`, `submitting` resets via `finally`, and the worker receives no toast whatsoever; (c) `src/lib/onboarding-store.tsx:126-204` — a failed hydration is swallowed (`:195-199`) leaving the store at `INITIAL_FULL`, so `/dashboard/menu` renders an empty editor over a live menu.
- Impact: (a) the operator cannot distinguish "no orders" from "the connection is dead" — the exact failure described in this slice's brief; (b) tapping "Place order" in a busy service simply does nothing visible and the order is never created; (c) a transient 500 on `/api/menu` makes the owner's menu appear erased, and the next edit then autosaves that empty-looking view (guarded only by `hasMenuContent`, `:84-85, 209`, which passes as soon as the name is present) — a plausible partial-wipe.
- Fix: give each surface an explicit error/offline state and render it; add a `catch` to `place` that toasts and keeps the dialog open; make the store distinguish "no menu yet" from "hydration failed" and refuse to autosave until hydration succeeds.

### FE-14 · Medium · useOrders optimistic mutations · VERIFIED
- Evidence: `src/lib/use-orders.ts:57-71` — `patch` awaits the PATCH but never inspects `res.ok`, and its `catch` is empty (`:66-68`, comment: "optimistic update already applied — next poll reconciles"). The callers mutate local state first and unconditionally (`acceptOrder` `:73-94`, `markOrderPaid` `:96-108`). The callers then toast success before/independently of the result (`src/app/(worker)/worker/dashboard/page.tsx:85, 90`; `src/app/(owner)/dashboard/orders/page.tsx:40, 45`).
- Impact: a cashier tapping Accept where the server returns 403/401/404 (or the order was already taken) sees the card move to Accepted and a green success toast; 3 seconds later the poll silently snaps it back to Pending. In local mode `patch` returns immediately (`:59`) and the false state is permanent. The worker is told they succeeded, then watches it undo itself with no explanation, and may re-attempt with a guest standing at the counter.
- Fix: await the PATCH, check `res.ok`, revert the local mutation on failure and replace the success toast with the server's `message`; retry once on 409 with a refresh. Do not toast before the response.
- Note: the same double-submit protection is absent on the order action buttons (`src/components/dashboard/order-card.tsx:73-95` have no `disabled`), but because the optimistic update removes the button on the first tap and the PATCH is idempotent server-side (`src/app/api/orders/[id]/route.ts:81-117`), this is not exploitable as-is — it becomes exploitable the moment FE-14 is fixed naively (revert-on-failure restores the button mid-flight). Fix both together.

### FE-15 · Medium · ForgotForm · VERIFIED
- Evidence: `src/components/forgot-form.tsx:17-28` — the `fetch` result is never inspected and `setSent(true)` runs in `finally`, so it runs on a network rejection too. `/api/auth/recover` returns `200 {cloud:true}` and does nothing when Supabase is unconfigured (`src/app/api/auth/recover/route.ts:21-23`).
- Impact: an owner locked out of their own restaurant is told "a reset link is on its way" with certainty, when nothing was sent and nothing can be sent (no `.env.local`, no Supabase project — the project's stated top blocker). They will wait, retry, and conclude the product is broken with no path forward. The enumeration-safe wording is correct for 2xx; claiming it for a failed request is not.
- Fix: keep the neutral copy for any response that indicates the request was accepted, but report a distinct failure for 5xx/network (and where the backend is unconfigured) with a support route instead of a false promise.

### FE-16 · Medium · App Router boundaries · VERIFIED
- Evidence: a full listing of `src/app` shows `layout.tsx`, `page.tsx`, the four `auth/*/page.tsx`, `onboarding/page.tsx`, `menu/[slug]/[token]/page.tsx`, the two route-group layouts and their pages — and no `not-found.tsx`, `error.tsx`, `loading.tsx` or `global-error.tsx`. `src/app/menu/[slug]/[token]/page.tsx:26` and `:49` call `notFound()` for an unknown slug or a token that does not belong to that restaurant.
- Impact: a guest who scans a QR from an old print run, or a token that was regenerated, lands on Next's unstyled default 404 — English-only, unbranded, with no "ask your server to rescan" guidance and no link back to the restaurant. For a seated phone user this is a hard dead end, and it is the most likely real-world failure (reprinted or reassigned tables). Any thrown error in any page produces the generic "Application error" screen with the same properties.
- Fix: add `src/app/not-found.tsx` (branded, i18n'd, with a rescan hint) and a route-level `error.tsx`; consider a `not-found` variant for the guest route that also renders the restaurant's name when the slug matched but the token did not.

### FE-17 · Medium · Guest menu, category editor, lang switcher — accessibility · VERIFIED
- Evidence: `src/components/guest-menu.tsx:413-429` (product stepper −/+) and `:627-641` (cart-sheet −/+) are icon-only `<button>`s with no `aria-label` and no text, inside a `p-0.5` box around a `w-3.5 h-3.5` icon — roughly 22 px including padding, against the 44 px touch guideline and below WCAG 2.2 target size (24 px). `src/components/onboarding/step-categories.tsx:135-152` sizes reorder arrows the same way and names them only via `title`. `src/components/lang-cur-switcher.tsx:15-41` is an unlabelled cluster of 10 px toggles with no `role="group"` and no `aria-pressed`, rendered on the guest menu header (`src/components/guest-menu.tsx:201`).
- Impact: a screen-reader user hears "minus, plus" repeated for every product with no way to tell which dish each belongs to, and cannot adjust a cart line at all; a thumb on a phone in a dim restaurant will mis-hit a 22 px target, and the stepper is the control the entire ordering flow depends on. The language/currency switcher gives no indication of which option is active.
- Fix: an i18n'd "increase/decrease <item name>" `aria-label` on every stepper button (the trash button in `worker-new-order.tsx:263-270` already models this with `aria-label={t("wo_removeLine")}`), pad the hit area to ≥44 px, and give the switcher `role="group"` with an accessible name plus `aria-pressed` on each toggle.

### FE-18 · Medium · I18nProvider — hydration · VERIFIED
- Evidence: `src/lib/i18n.tsx:1828-1835` reads `window.localStorage` inside a `useState` initializer, while the server branch returns the hard-coded default `"en"` / `"tnd"` (`:1829, 1833`). `suppressHydrationWarning` is set on `<html>` only (`src/app/layout.tsx:19`), which covers that element's own attributes, not mismatched text in descendants; `document.documentElement.lang/dir` are applied in an effect afterwards (`:1843-1844`).
- Impact: every user whose stored language is `fr` or `ar` — the two locales the product explicitly ships, including the whole Tunisian target market — renders English HTML on the server, then hydrates with French/Arabic strings. React logs a hydration error and re-renders the affected subtree client-side, producing a visible flash of the wrong language on every load, on every route, including the guest menu. The RTL direction is likewise applied one frame late.
- Fix: render the server default and switch language in an effect (accepting a flash of the default), or — preferred — persist the language in a cookie and read it in the root layout so server and client agree; set `lang`/`dir` on `<html>` from that cookie.

### FE-19 · Low · ProductForm / invite accept — silent validation · VERIFIED
- Evidence: `src/components/onboarding/step-products.tsx:47-59` returns without any message when the name is blank, the price does not parse, or no category is selected; the submit button is disabled on `!name.trim() || !price || !categoryId` (`:154`), and `!price` is true for the string `"0"`, so a legitimately free item (a 0.000 DT line) can never be added. `src/app/(worker)/worker/invite/[token]/page.tsx:116` does the same: `if (!cleanName) return;` with no feedback, and the Accept button (`:270-279`) is only disabled while `working`.
- Impact: a worker tapping "Accept invitation" with the name field untouched sees absolutely nothing happen and has no idea a name is required — the accept form has no `required` attribute and no error slot. An owner adding a free item is blocked with a disabled button and no explanation.
- Fix: add field-level error text (`aria-describedby`), a `required` attribute on the invite name field, and test `price.trim() === ""` instead of a falsy check.

### FE-20 · Low · onboarding-store `acceptInvite` · INFERENCE
- Evidence: `src/lib/onboarding-store.tsx:496-523` calls `setWorkerSession(...)` at `:505` from inside the `set((s) => …)` updater passed to `setState`, i.e. a state update and a `localStorage` write performed during another state update's computation rather than in the event handler.
- Impact: [INFERENCE] React is permitted to invoke updaters more than once (StrictMode double-invoke, concurrent re-render), so the localStorage write and the `setWorkerSession` call are not guaranteed to run exactly once per accept. The practical blast radius is small because the last invocation wins, but the pattern is not safe to rely on and the worker id persisted is whatever the final invocation generated.
- Fix: compute the worker object in the handler, call `setWorkerSession(worker)` outside the updater, then apply the invite/worker list changes.

## Guest gets stuck — numbered failure list

Reproduction from a phone that has just scanned a table QR (`/menu/<slug>/<token>`), assuming the happy path works up to the stated step.

1. **Cart lost on refresh.** Add 3 items → pull to refresh (or the phone reclaims the tab). The cart is `useState` (`guest-menu.tsx:59`), so it returns empty. No warning, no restore. *Recovery: none beyond rebuilding the cart.* → FE-05
2. **Order number lost on refresh of the confirmation screen.** Submit → "Order #12, 24.500 DT" appears → refresh (or back-swipe, or lock the phone long enough for eviction). The overlay is `useState` (`:62`) and the guest has no read access to `/api/orders` (`api/orders/route.ts:38-40`). The order exists, the guest can no longer prove it or check it. *Recovery: ask staff to search manually.* → FE-05
3. **Duplicate order after a timeout.** Submit → the client shows "Network error" (the request actually committed) → tap "Send order" again → a second real order is created, because `clientRef` is regenerated per attempt (`guest-menu.tsx:125`), defeating the server's `client_ref` idempotency guard (`api/orders/route.ts:368-404`). *Recovery: the guest must find a staff member and cancel a duplicate they cannot see.* → FE-03
4. **Stuck on 409 (item went unavailable).** Submit an item that another device marked unavailable mid-session → toast "Some items are no longer available." with no product named (`:138-143`, `api/orders/route.ts:158-159`). The item is still displayed and still in the cart, because the list was server-rendered with `is_available = true` at load (`menu/[slug]/[token]/page.tsx:39`) and never refreshes. *Recovery: only by guessing which line to delete, or reloading — which destroys the cart (failure 1).* → FE-04
5. **Stuck on 404 (item deleted from the menu).** Identical mechanism, message "Some items are no longer on the menu." (`api/orders/route.ts:156`). Same dead end. → FE-04
6. **429 rate limit.** Server returns `429 {message: "Too many orders. Try again in Ns."}` (`api/orders/route.ts:192-202`) and the client does toast it (`guest-menu.tsx:138-142`). *Recoverable* — but only if the body parses as JSON: any intermediary returning a non-JSON 429 makes `await res.json()` throw into the same `catch` as a transport failure (`:144-145`), so the guest is told "Network error" instead of "wait N seconds" and retries immediately, deepening the limit. → FE-13(b)
7. **Bad token / unknown table (404 page).** Scan a QR from an old print run, or a token whose restaurant no longer matches → `notFound()` (`menu/[slug]/[token]/page.tsx:26, 49`). With no `not-found.tsx` in the app, the guest gets Next's default unstyled English 404 with no restaurant context and no guidance to ask staff to rescan. *Recovery: none.* → FE-16
8. **Menu is live but the restaurant was never created.** The owner printed QR codes in a session where the first `PUT /api/menu` failed (slug collision or 5xx) yet the UI reported "Saved locally" and the wizard reported "Live" (`save-status.tsx:11-18`, `step-preview.tsx:118-121`). The guest's correct-looking QR leads to failure 7. *Recovery: none; the QR is permanently dead.* → FE-02, FE-11
9. **Ordering disabled for the whole deployment.** With Supabase unconfigured, the page renders `<GuestMenu unavailable />` (`menu/[slug]/[token]/page.tsx:16-18`) — a dark screen telling the guest the menu is not live, with no alternative and no way to see the restaurant's offering. Intentional, but it means the only guest-visible surface of the product is a dead end in the current repo state. → (by design; no fix proposed)

Not a stuck state but worth recording: 404 on an unknown *slug* and 404 on a *bad table token* are indistinguishable to the guest, and neither is logged anywhere the owner can see.

## Open questions

1. Was `/onboarding` intended to be usable before signup (a lead-gen funnel that ends in a signup wall), or should it be behind the owner guard? The code contains no signup hand-off either way, so both readings currently end in a dead end — FE-01/FE-09. The answer decides whether the fix is a redirect or a signup step.
2. Is the `isCloud`-once hydration (FE-08) deliberately "menu-authored ⇒ cloud mode", with the assumption that every real owner always passes through the wizard? If so, the assumption is undocumented and fails for any owner who signs in on a second device.
3. Is the worker dashboard supposed to be usable with no server session at all (a genuine offline terminal), or is the local fallback meant only for the demo? `worker-shell.tsx:18-21` and `layout.tsx:4-9` describe an intentional offline demo mode, but the fallback also triggers on 429/5xx (FE-06), which is what makes FE-07 exploitable rather than merely a demo affordance.
4. `src/lib/menu-mapping.ts:107` always writes `isPublished: true` and the guest route never checks `is_published`. Is a draft/published state a product requirement at all? If yes, the guest route needs the filter and the wizard needs a real control; if no, the "draft"/"Live" badges in `step-preview.tsx:104, 120` should be removed rather than wired up.
5. Should the guest be able to see their own order status after submitting? Nothing in the client or the API supports it today, so it is out of scope for this audit — but failure 2 cannot be fully fixed without it, only mitigated by persisting the confirmation.
